# v0.10.1 — 取消初始化（删 `.git`）+ 三个问题的答案

> 2026-10-19 · 增量版本，只动 git 侧 · 自测 host **166** + client **548** 全通过

## 这一版加了什么

只有一件事：**「取消初始化」按钮**。

0.10.0 能把项目「初始化成仓库」，但反过来没路 —— 用户只能自己去终端敲 `rm -rf .git`。
现在「⑂ 源代码管理 → 分支」视图底部有危险区：

- 按钮文字是 **删除 .git（取消初始化）**
- 点第一次变成 **再点一次确认删除 .git**（4 秒不点自动复原）
- 下面一行小字写清了后果：项目文件一个都不动，只删 `.git`；历史 / 分支 / 标签一起没掉；
  已推到 GitHub 的那份不受影响，随时能重新克隆回来

### 服务端的三条硬约束

UI 的二次确认不算防线，服务端另拦三道（`gitUninit`）：

| 约束 | 拒绝理由 | 为什么 |
|---|---|---|
| 必须 `confirm: true` | `删除 .git 需要显式确认` | 不信 UI 默认值，防止别处误调 |
| 必须在仓库根 | `只能在仓库根目录取消初始化（当前在子目录）` | 在子目录放开 = 把上层仓库连锅端 |
| `.git` 必须是目录 | `这是 worktree 或子模块的 .git 文件…` | `.git` 是文件说明它指向主仓库，删了会连带毁掉主仓库；符号链接同理 |

另外，主仓库里挂了 worktree 时（`.git/worktrees` 有内容）返回里会带 `hadWorktrees: true` ——
只删主 `.git` 会让那些 worktree 变孤儿，这里**提醒但允许**，因为用户可能就是想清干净。

删除用的是 `rmSync(..., { recursive: true, force: true })`，只针对 `.git` 这一个路径，
不是对整个项目目录动手。

## 路由

`POST /api/trae-worktable/git`，`op: 'uninit'`：

```json
{ "path": "D:/code/my-proj", "op": "uninit", "confirm": true }
```

| 结果 | HTTP | body |
|---|---|---|
| 成功 | 200 | `{ ok: true, removed: "D:/code/my-proj/.git", hadWorktrees: false }` |
| 没确认 / 在子目录 / 不是目录 | 400 | `{ ok: false, error: "…" }` |
| 目录不在可写白名单内 | 403 | 沙箱拦截（`uninit` 已加入 `GIT_WRITE_OPS`） |

删完之后 `op: 'status'` 会回到 `{ ok: true, repo: false }` —— 界面自动变回「还不是 git 仓库」，
旁边就是「在这里初始化仓库」和「克隆一个仓库」。

## 顺带回答的两个问题

### 1. 怎么删除「初始化过的仓库」

三种粒度，别混：

| 想做什么 | 怎么做 | 结果 |
|---|---|---|
| 只取消 git，文件全留 | 源代码管理 → 分支 → 删除 .git（这一版新增） | 变回普通文件夹 |
| 连文件一起删（克隆下来的仓库） | 文件窗格里删目录，或系统文件管理器 | 目录整个消失 |
| 只是不想在工作台里看到它 | 项目右键 → 从工作台移除 | **磁盘不动**，只是从列表里拿掉 |

这一步最容易被误解的是第三种 —— 「从工作台移除」从来不删磁盘。

### 2. 能不能直接照搬 VS Code 的 git？

不能直接搬代码，但**功能清单可以照搬**，而且这件事 0.10.0 已经做了大半。

**为什么不能搬：**

- VS Code 的 git 是内置扩展（`extensions/git`），代码是 MIT 的，法律上能用；但它通篇依赖
  VS Code 自己的 API —— `vscode.scm` 的 SourceControl / ResourceGroup / InputBox 状态机、
  TreeView、`vscode.diff` 虚拟文档、QuickPick。这些在 DSH 的 Cordis 插件里一个都不存在，
  搬过来等于把整个 VS Code 的 UI 框架也搬过来。
- 真正能「照搬」的是**协议层**：它内部跑的就是 `git` 命令 + porcelain 解析，
  这块我们已经自己实现了（`src/git.js`，`--porcelain=v1 -z` 零分隔解析），逻辑思路一致。

**还差什么（按性价比排）：**

| 差距 | 难度 | 做法 |
|---|---|---|
| 按 hunk / 按行暂存 | 中 | `git diff` 拿 patch → 抠出选中的 hunk 拼新 patch → `git apply --cached` |
| 冲突解决（用我的 / 用他的） | 低 | `git ls-files -u` 读冲突 → `git checkout --ours/--theirs -- <f>` → `git add`。UI 里 `conflicts` 组已经能读出来了，只缺按钮 |
| Amend / 撤销上次提交 | 低 | `commit --amend` / `reset --soft HEAD~1`，参数 `gitCommit` 已经有 `amend` 了，只差 UI |
| Stash | 低 | `git stash push/pop/list`，加三个 op 即可 |
| 行内 gutter 改动标记 | 高 | 要在编辑器里做装饰层，DSH 目前没有可注入的编辑器 API |
| 提交图（graph） | 高 | `git log --graph` 的 ASCII 图能直接渲染，但交互式图要自己画布局 |
| 三方合并编辑器 | 很高 | VS Code 那套是独立组件，不建议复刻 |

所以路线是：**照搬它的功能形态，不照搬它的实现**。下一步如果继续做，冲突解决和 stash
是两个「工作量小、感知强」的点。

## 升级方式

```powershell
& "<你的 DSH 安装目录>\resources\runtime\cli\bin\dsh.cmd" plugin --profile desktop add "https://github.com/nscn6fdx44-crypto/dsh-worktable/releases/download/v0.10.1/trae-usage-worktable-0.10.1.tgz"
```

装完**完整退出 DSH 再启动**（`uninit` 是 host 侧新 op，不重启会走到旧的白名单分支）。
